# 3단계: 글자 검색 PDF (OCR)

## 동작

- 문서 화면 → 내보내기 → "글자 검색·복사 가능한 PDF (OCR, 한국어·영어)"를 켜고 PDF를 만든다. 이 선택은 기기에 기억된다.
- 각 페이지의 결과 이미지를 기기 안에서 읽어(Tesseract.js 7, `kor+eng`, best_int 모델), 단어 위치에 보이지 않는 글자를 PDF에 넣는다. 화면에 보이는 것은 그대로 스캔 이미지다.
- 읽은 결과는 페이지와 함께 보관함에 저장되어 다음 PDF부터는 다시 읽지 않는다. 페이지를 다시 맞추거나 모드를 바꿔 저장하면 결과 이미지가 바뀌므로 OCR도 지워지고 다음 PDF 때 다시 읽는다.

## 구성

| 파일 | 역할 |
|---|---|
| `src/lib/textLayer.ts` | 보이지 않는 글자층. 빈 글리프 하나뿐인 628바이트 TrueType 글꼴을 Type0/Identity-H로 넣고, 각 글자를 UTF-16 코드로 쓴다(ToUnicode가 같은 코드로 되돌림). 한글 글꼴을 넣지 않아도 어떤 문자든 검색·복사된다. 단어마다 글자 폭(Tz)을 맞춰 단어 상자 위에 놓는다. |
| `src/lib/ocr.ts` | Tesseract 결과 → 줄·단어 상자. 한국어 모델이 음절 단위로 쪼갠 단어("음 악 학 원")와 숫자·단위("2026 년")를 간격으로 판단해 다시 붙인다(글자 간격은 글자 높이의 0.1~0.25, 띄어쓰기는 0.37~0.6 → 기준 0.32). |
| `src/ocr.ts` | 브라우저 쪽. 긴 변이 3000px보다 작은 페이지는 최대 2배 확대해서 읽는다(작은 이미지에서 한국어 단어를 통째로 잘못 읽는 문제: 1240px 페이지에서 "음악학원" → "SE"). |
| `vite.config.ts` (`ocrFiles`) | 워커, SIMD 코어(WASM), 한국어·영어 모델을 앱의 `ocr/`에서 직접 제공. 외부 CDN 접속 없음. 서비스 워커는 처음 쓸 때 받아서 보관(설치 시 미리 받지 않음). |

내려받는 양(처음 OCR을 쓸 때 한 번): 코어 2.9 MB + 한국어 1.6 MB + 영어 3.0 MB + 워커 0.2 MB ≈ 7.7 MB.

## 확인

- `test/textlayer.test.ts`: 만든 PDF에서 poppler(`pdftotext`)로 한글·영문·기호가 그대로 나오고, 단어 위치가 상자와 3pt 이내로 맞는지. pdfium에서도 글자 상자가 정확히 맞고, 렌더링하면 아무것도 보이지 않음을 따로 확인.
- `test/ocr.test.ts`: 실제 Tesseract로 한국어·영어 시험 페이지 읽기(띄어쓰기 포함 원문과 동일), 작은 스캔 이미지는 확대해야 맞게 읽는지.
- 브라우저 종단 테스트: 사진 → 페이지 → OCR PDF → `pdftotext` 결과가 원문과 같음. 1쪽 약 1.5~2초(이 서버 기준). 두 번째 PDF는 저장된 결과를 써서 0.1초. 새로고침 뒤에도 유지. 외부 호스트 요청 없음.

## 실기기에서 볼 것

- iPhone에서 한 쪽 읽는 시간, 여러 쪽(10쪽 이상)일 때 메모리.
- 파일 앱 / 미리보기에서 PDF 검색과 글자 선택·복사가 되는지.
- 실제 사진(조명 얼룩, 작은 글씨, 표)에서 인식률.
